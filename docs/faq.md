# Frequently asked questions

### Is this a replacement for BPMN, UML, SysML or cloud architecture diagrams?

No. UL-xDFD preserves DFD data semantics and links other concerns through typed references. A BPMN process can remain the authority for execution ordering, an OpenAPI file for interface contracts, and a provider invoice for billed cost.

### Why not put every annotation directly on the drawing?

Real systems have too many independent concerns. The canonical graph can store detailed, evidence-backed values while each view displays only the information a reader needs.

### Can the model predict the success of a DevOps adoption project?

Not yet. The present proposal supports diagnostics and future research into prediction. Success probabilities need defined outcomes, frozen baseline measurements, representative data and external validation.

### Does a complicated DFD imply poor readiness?

No. Graph size, service count, organizational culture and delivery performance measure different things. Complexity can indicate analysis effort, not a universal maturity score.

### Can the current Python script calculate cloud or AI costs?

No. The bundled script performs basic structural validation only. Cost equations and metering requirements are specified for future engines.

### How are multi-agent systems represented?

With separate agent definitions, run identities, delegations, tool calls, policies, outcomes, and evidence. MCP and A2A are modeled only when actually used; protocol compatibility must be checked outside the drawing.

### Can we use UL-xDFD without cloud telemetry?

Yes, for a design-stage model, but forecasts must show their assumptions and uncertainty. An `estimated` or `hypothetical` figure must not be relabeled as observed.

### Can this become an official standard?

It could be proposed to a standards organization in the future, but no official designation is claimed. Current terms such as MUST apply only to this project's proposed conformance contract.
